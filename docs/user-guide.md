# Посібник користувача rental-is

rental-is — система подобової оренди житла. Посібник описує роботу гостя, власника й модератора через Swagger UI. Це єдиний інтерфейс поточної версії.

Терміни вжито так, як у [глосарії](../spec/glossary.md):

| Термін | Значення |
|--------|----------|
| Житло, оголошення, картка житла | Та сама сутність: те, що публікує власник |
| Запит | Бронювання в статусі PENDING, яке чекає рішення власника |
| Бронювання | Запис у будь-якому статусі: PENDING, CONFIRMED, REJECTED, CANCELLED, COMPLETED |
| Ніч | Календарна дата проживання. Дата виїзду до ночей бронювання не входить |
| Вартість проживання | Кількість ночей × ціна за ніч, без комісії |
| Передоплата | Вартість проживання + комісія |

Статуси бронювання:

| Статус | Що означає |
|--------|------------|
| PENDING | Запит чекає рішення власника |
| CONFIRMED | Власник підтвердив запит |
| REJECTED | Запит відхилено власником або автоматично |
| CANCELLED | Скасовано гостем або власником |
| COMPLETED | Настав момент виїзду, проживання завершено |

## 1. Початок роботи

### 1.1. Відкрити Swagger UI

Запустіть сервер із тестовими токенами, як описано в [README](../README.md#запуск-сервера), і відкрийте в браузері `http://127.0.0.1:8765/docs`.

Усі операції показано одним списком у розділі **default**. Біля операцій, де можна виконати вхід, є значок замка.

### 1.2. Увійти через Authorize

Реєстрації та входу за паролем у цій версії немає. Роль визначає тестовий токен:

| Роль | Токен |
|------|-------|
| Гість | `guest-token` |
| Власник | `host-token` |
| Модератор | `moderator-token` |

1. Натисніть кнопку **Authorize** угорі сторінки.
2. У полі **Value** введіть токен, без слова `Bearer`.
3. Натисніть **Authorize**, потім **Close**.

Щоб змінити роль, знову натисніть **Authorize**, потім **Logout** і введіть інший токен.

Токен позначає одного користувача. Гість, власник і модератор у наведених сценаріях — це три різні користувачі.

### 1.3. Виконати операцію

1. Розгорніть операцію в списку, наприклад **POST /bookings Create Booking**.
2. Натисніть **Try it out**.
3. Заповніть параметри або поле **Request body**.
4. Натисніть **Execute**.
5. Результат показано в блоці **Server response**: стовпець **Code** містить код відповіді, а **Details** — тіло й заголовки.

Коди 200 і 201 означають успіх. Про інші коди див. [розділ 5](#5-типові-відмови). Блок **Responses** під кнопкою **Execute** перелічує лише код успіху й 422, а для частини операцій 422 узагалі неможливий. Фактичний результат показано в **Server response**. Повний перелік кодів кожної операції містить `docs/api.html`.

Дати вводьте у форматі `РРРР-ММ-ДД`. Усі дати й час задано в часовому поясі Europe/Kyiv.

Ідентифікатори житла й бронювань (`id`) беріть із **Response body** попередніх операцій.

Дані зберігаються лише під час роботи сервера. Після перезапуску всі оголошення й бронювання зникають.

## 2. Гість

### 2.1. Пошук житла

Операція: **GET /listings Search Listings**. Вхід не потрібен. Пошук показує лише житло в стані Published.

Усі фільтри необов'язкові й поєднуються довільно.

| Параметр | Що задає | Значення |
|----------|----------|----------|
| `city` | Місто | Точний збіг без урахування регістру |
| `checkIn`, `checkOut` | Діапазон дат | Задаються лише разом. У результаті лишається житло, доступне на весь діапазон |
| `guestsCount` | Кількість осіб | Ціле число від 1 |
| `priceMin`, `priceMax` | Межі ціни за ніч | Два знаки після крапки, наприклад `1500.00` |
| `sort` | Порядок | `price_asc` — ціна за зростанням, `price_desc` — ціна за спаданням, `rating_desc` — середня оцінка за спаданням |
| `limit` | Розмір сторінки | Від 1 до 100, за замовчуванням 20 |
| `offset` | Скільки записів пропустити | Від 0, за замовчуванням 0 |

**Перегляд сторінками.** Загальну кількість знайденого показує заголовок `X-Total-Count` у блоці **Response headers**. Браузер може показати його малими літерами. Значення не залежить від `limit` і `offset`.

Щоб переглянути результат сторінками по 10 записів:

1. Виконайте пошук із `limit` = 10 і `offset` = 0.
2. Подивіться значення `X-Total-Count`.
3. Для наступної сторінки збільште `offset` на 10 і знову натисніть **Execute**.

Якщо `offset` більший за кількість знайденого, результат буде порожнім `[]`, це не помилка. Без `sort` і для однакових значень ключа сортування житло йде в порядку створення.

### 2.2. Перегляд картки житла

Операція: **GET /listings/{listingId} Get Listing**. Вхід не потрібен. Вкажіть `listingId` і натисніть **Execute**.

Житло, зняте з публікації, бачать лише його власник і модератор. Для решти відповідь буде 404 `NOT_FOUND`.

### 2.3. Бронювання

Операція: **POST /bookings Create Booking**. Увійдіть як гість і вкажіть у **Request body**:

```json
{
  "listingId": "ідентифікатор житла",
  "checkIn": "2027-06-10",
  "checkOut": "2027-06-12",
  "guestsCount": 2
}
```

Успішна операція повертає код 201 і запит у статусі PENDING. На ті самі ночі може існувати кілька запитів: дати зайнято лише після підтвердження.

У запиті зафіксовано умови на момент створення. Пізніші зміни картки житла на нього не впливають.

| Поле відповіді | Значення |
|----------------|----------|
| `accommodationCost` | Вартість проживання |
| `commissionRate` | Відсоток комісії |
| `commission` | Комісія, округлена вниз до 0,01 грн |
| `prepayment` | Передоплата |
| `checkInAt`, `checkOutAt` | Момент заїзду й момент виїзду |
| `decisionDeadline` | Строк рішення власника |

Приклад: 2 ночі по 1500.00 грн дають вартість проживання 3000.00 грн, комісію 10% — 300.00 грн і передоплату 3300.00 грн.

**Строк рішення власника** — найраніший із двох моментів: 24 години після створення запиту або момент заїзду. Якщо власник не вирішив до цього моменту, запит автоматично переходить у REJECTED.

Причини відмови описано в [розділі 5](#5-типові-відмови).

### 2.4. Мої поїздки

Операція: **GET /bookings List Bookings**. Увійдіть як гість і оберіть у списку `role` значення `guest`.

Відповідь містить усі ваші бронювання: дати, статус і передоплату. Житло вказано ідентифікатором `listingId`, а назву можна дізнатися через **Get Listing**.

Окреме бронювання показує **GET /bookings/{bookingId} Get Booking**. Чуже бронювання недоступне: відповідь буде 404 `NOT_FOUND`.

### 2.5. Скасування й частка повернення

Операція: **POST /bookings/{bookingId}/cancel Cancel Booking**. Вкажіть `bookingId` і натисніть **Execute**. Бронювання перейде в CANCELLED, а поля `cancelledBy` і `cancelledAt` покажуть, хто й коли його скасував.

Гість може скасувати свій запит у PENDING або своє бронювання в CONFIRMED. У момент заїзду й пізніше скасування неможливе. Бронювання в статусах REJECTED, CANCELLED і COMPLETED скасувати не можна.

Частка повернення залежить від ініціатора, попереднього статусу й часу t до моменту заїзду:

| Хто скасовує | Попередній статус | Час до моменту заїзду | Частка повернення |
|--------------|-------------------|-----------------------|-------------------|
| Гість | PENDING | Будь-який | 100% |
| Гість | CONFIRMED | t ≥ 168 год (7 діб) | 100% |
| Гість | CONFIRMED | 72 год ≤ t < 168 год | 50% |
| Гість | CONFIRMED | t < 72 год | 0% |
| Власник | CONFIRMED | Будь-який | 100% |

Сума повернення — це частка від вартості проживання плюс частка від комісії. Кожен доданок округлюється вгору до 0,01 грн. Приклад: для передоплати 3300.00 грн із вартістю проживання 3000.00 грн і комісією 300.00 грн частка 50% дає 1500.00 + 150.00 = 1650.00 грн.

У цій версії відповідь **Cancel Booking** не показує ні частку, ні суму повернення, а платіжних операцій немає. Див. [розділ 6](#6-обмеження-версії).

## 3. Власник

### 3.1. Створення оголошення

Операція: **POST /listings Create Listing**. Увійдіть як власник і замініть приклад у **Request body**. Фрагмент у `photos` — це готове зображення PNG для перевірки.

```json
{
  "title": "Квартира на Подолі",
  "description": "Біля метро",
  "city": "Київ",
  "address": "вул. Сагайдачного, 1",
  "maxGuests": 4,
  "pricePerNight": "1500.00",
  "photos": [
    {"data": "iVBORw0KGgoAAAANSUhEUgAAAAEAAAABCAYAAAAfFcSJAAAADUlEQVR42mNkYPhfDwAChwGA60e6kgAAAABJRU5ErkJggg=="}
  ],
  "checkInTime": "14:00",
  "checkOutTime": "11:00",
  "turnoverNights": 0
}
```

Оголошення одразу отримує статус PUBLISHED і з'являється в пошуку. Той, хто його створив, стає власником.

| Поле | Вимоги | За замовчуванням |
|------|--------|------------------|
| `title` | Обов'язкове, до 100 символів | — |
| `description` | Необов'язкове, до 2000 символів | — |
| `city`, `address` | Обов'язкові | — |
| `maxGuests` | Максимальна кількість осіб, від 1 до 20 | — |
| `pricePerNight` | Від 0.01 до 1000000.00, два знаки після крапки, у лапках | — |
| `photos` | Від 1 до 10 фотографій JPEG або PNG, кожна не більше 5 МБ (5 242 880 байтів). Нова фотографія подається в полі `data` у форматі base64 | — |
| `checkInTime` | Час заїзду, 12:00–20:00 | 14:00 |
| `checkOutTime` | Час виїзду, 08:00–12:00 | 11:00 |
| `turnoverNights` | Технологічна перерва: 0 або 1 ніч після виїзду кожного бронювання | 0 |

### 3.2. Редагування оголошення

Операція: **PUT /listings/{listingId} Replace Listing**. Редагувати можна лише власне оголошення.

Операція повністю замінює картку, тому передайте всі поля, зокрема незмінені. Необов'язкове поле, якого немає в **Request body**, скидається: опис зникає, а час заїзду, час виїзду й перерва повертаються до значень за замовчуванням.

Щоб залишити наявну фотографію, вкажіть її `id` із картки:

```json
"photos": [{"id": "ідентифікатор фотографії"}]
```

Нову фотографію додають через `data`. Фотографія, якої немає в списку, вилучається. Уже створені запити й бронювання зберігають умови, зафіксовані раніше.

### 3.3. Запити й бронювання власного житла

Операція: **GET /bookings List Bookings**. Увійдіть як власник і оберіть у списку `role` значення `owner`. У відповіді будуть запити й бронювання вашого житла у всіх статусах.

### 3.4. Підтвердження або відхилення запиту

Операції:

- **POST /bookings/{bookingId}/confirm Confirm Booking** — підтвердити;
- **POST /bookings/{bookingId}/reject Reject Booking** — відхилити.

Вирішити можна лише запит у статусі PENDING на власне житло і до спливу строку рішення.

Підтвердження переводить запит у CONFIRMED. Інші запити в PENDING, несумісні з ним, автоматично переходять у REJECTED. Запит із заїздом у день виїзду підтвердженого бронювання сумісний, якщо технологічна перерва дорівнює 0.

Відхилення переводить запит у REJECTED. Гість отримує 100% передоплати за правилами системи, див. також [розділ 6](#6-обмеження-версії).

### 3.5. Скасування підтвердженого бронювання

Операція: **POST /bookings/{bookingId}/cancel Cancel Booking**. Власник може скасувати лише бронювання в CONFIRMED на своє житло і до моменту заїзду. Частка повернення гостю становить 100%, поле `cancelledBy` матиме значення `HOST`.

## 4. Модератор

Модератор працює з оголошеннями. Він не може створювати оголошення й запити, а також не бачить бронювань.

### 4.1. Зняття оголошення з публікації

Операція: **POST /listings/{listingId}/unpublish Unpublish Listing**. Увійдіть як модератор, вкажіть `listingId` і підставу в **Request body**:

```json
{"reason": "Оголошення порушує правила платформи"}
```

Підстава обов'язкова. Наслідки зняття:

- оголошення отримує статус UNPUBLISHED і не показується в пошуку;
- нові запити на це житло отримують відмову `LISTING_UNPUBLISHED`;
- запити в PENDING переходять у REJECTED;
- бронювання в CONFIRMED зберігаються й виконуються.

### 4.2. Повернення в публікацію

Операція: **POST /listings/{listingId}/publish Publish Listing**. Формат **Request body** такий самий. Оголошення знову отримує статус PUBLISHED. Запити, відхилені під час зняття, не відновлюються.

## 5. Типові відмови

Під час відмови **Response body** містить поле `code` з кодом причини й поле `detail` з поясненням.

### 5.1. Відмова у створенні запиту

Запит не створюється, а система повертає першу причину, яка спрацювала, у порядку таблиці.

| Код | HTTP | Що сталося | Що зробити |
|-----|------|------------|------------|
| `NOT_FOUND` | 404 | Такого житла немає | Перевірте `listingId` |
| `MIN_NIGHTS` | 422 | Менше 1 ночі: `checkOut` дорівнює `checkIn` або раніший за нього | Вкажіть дату виїзду, пізнішу за дату заїзду |
| `OWN_LISTING` | 403 | Ви намагаєтеся забронювати власне житло | Оберіть інше житло |
| `GUESTS_OUT_OF_RANGE` | 422 | `guestsCount` менше 1 або більше за максимальну кількість осіб у картці | Вкажіть допустиму кількість осіб |
| `LISTING_UNPUBLISHED` | 409 | Житло зняте з публікації | Оберіть інше житло |
| `CHECKIN_TOO_SOON` | 422 | До моменту заїзду менше 1 години, або дата заїзду минула | Оберіть пізнішу дату заїзду |
| `DATES_UNAVAILABLE` | 409 | Діапазон перетинається з бронюванням у статусі CONFIRMED або COMPLETED чи потрапляє в технологічну перерву. Поле `conflictingBookingIds` містить ці бронювання | Оберіть інші дати |

### 5.2. Інші відмови

| Код | HTTP | Що сталося | Що зробити |
|-----|------|------------|------------|
| `UNAUTHENTICATED` | 401 | Вхід не виконано або токен невідомий | Виконайте вхід через **Authorize** |
| `FORBIDDEN` | 403 | Дія недоступна вашій ролі або ви не власник цього житла | Увійдіть із потрібною роллю |
| `NOT_FOUND` | 404 | Ресурсу немає або він вам недоступний | Перевірте ідентифікатор і роль |
| `STATE_CONFLICT` | 409 | Дія неможлива в поточному стані: запит уже не в PENDING, оголошення вже зняте чи опубліковане, бронювання не можна скасувати або настав момент заїзду | Оновіть дані через **Get Booking** або **Get Listing** |
| `PHOTO_INVALID` | 422 | Фотографій немає або більше 10, формат не JPEG і не PNG, файл більший за 5 МБ, некоректний base64 або чужий `id` | Виправте `photos`; номер фотографії вказано в `detail` |
| `VALIDATION_FAILED` | 422 | Дані не відповідають формату: задано лише одну дату пошуку, дата виїзду не пізніша за дату заїзду в пошуку, ціна без двох знаків після крапки, зайве поле тощо | Виправте поле, назване на початку `detail` |
| `INTERNAL_ERROR` | 500 | Збій системи | Повторіть дію пізніше |

## 6. Обмеження версії

Операції, яких немає в цьому списку, не показано у Swagger UI. Звернення до них повертає 404 `NOT_FOUND`.

| Функція | Стан у цій версії |
|---------|-------------------|
| Закриті ночі (`closed-nights`) | Не реалізовано. Власник не може закрити ночі в календарі доступності |
| Платежі | Не реалізовано. Система лише показує `accommodationCost`, `commission` і `prepayment`: гроші не списуються й не повертаються, платіжних операцій та виплат власнику немає. Частку й суму повернення з [розділу 2.5](#25-скасування-й-частка-повернення) у відповідях не показано |
| Відгуки | Не реалізовано. Поле `averageRating` завжди `null`, тому сортування `rating_desc` не змінює порядок |
| Реєстрація та вхід | Не реалізовано. Користувачів задають три тестові токени |
| Спори, скарги на відгуки, оскарження | Не реалізовано |
| Блокування користувачів | Не реалізовано |
| Журнал подій і повідомлення | Не реалізовано. Про рішення власника можна дізнатися лише через **Get Booking** або **List Bookings** |
| Фотографії | Система перевіряє файл і видає `url`, але не зберігає зображення, тому за цим `url` файл не відкривається |
